Week 4 Deep Dive — Software Engineer Discipline

The Software Engineer Field Guide

You are not becoming a software engineer. You are becoming the person who directs, evaluates, and approves what AI-generated software engineering produces. This guide teaches the ~20% of the discipline that carries 80% of the judgment calls an AI Solution Architect makes: reading a design before it's built, spotting a module boundary that will rot in six months, and knowing whether a pull request is safe to merge.

The Scenario We'll Use Throughout

Every document in this guide is written against one concrete, believable feature so you can practice the discipline against something real instead of an abstraction.

The Feature: ClaimSense

Industry: Insurance (Property & Casualty). Feature: ClaimSense — AI-Assisted Claims Intake & Triage. When a policyholder submits a claim — a fender-bender photo from a mobile app, a water-damage email with attachments, or a portal form — ClaimSense ingests the documents, uses OCR and an LLM extraction step to pull structured fields (policy number, loss date, loss type, estimated damage), classifies the claim by type and severity, scores it for fraud and risk indicators, and routes it to the correct adjuster queue with an SLA clock running. A human adjuster always makes the final call on anything flagged or high-value — ClaimSense triages, it does not decide.

As the AI Solution Architect on this feature, you will not write the extraction service or the routing engine yourself. An AI coding agent (or a team using one) will. Your job is to have already decided — before a line of code exists — what "correct" looks like, and then to recognize whether what comes back matches it.

The 20% to Know

Software engineering has decades of accumulated practice. Most of it is mechanical — syntax, framework APIs, build tooling — and an AI agent handles that faster and more reliably than a human ever will. The 20% that remains is judgment: the part where someone has to decide what "good" means and recognize when it's missing. That's this section.

Technical Design Documents

A Technical Design Document (TDD) is the artifact that exists before code, so that expensive mistakes get caught on paper instead of in production. It states the problem, the chosen approach (and the approaches rejected, and why), the module breakdown, the data model, and the risks. If an AI agent starts writing code with no TDD behind it, you are approving architecture by accident, one file at a time, and you will not notice the accident until it's expensive to undo.

Architect's rule

No TDD, no build. If an AI agent proposes to "just start coding," the first output you require is the design doc — see ClaimSense's Technical Design Document for what a real one looks like.

Modularity & Separation of Concerns

A module should do one thing and be nameable in a sentence without the word "and." RiskScoringEngine computes a risk score. It does not also send the adjuster an email — that's NotificationService's job. When one module's name needs "and" to describe honestly, it's really two modules wearing a trenchcoat, and it will be twice as hard to test and twice as risky to change.

Separation of concerns is what makes an AI agent's output reviewable at all. A 1,400-line file that extracts documents, classifies claims, scores risk, and sends emails cannot be reviewed in a normal PR — it can only be trusted or not trusted. Small, single-purpose modules can actually be read.

Interfaces & Contracts

A contract is the promise a module makes about its inputs, its outputs, and the errors it can raise — independent of how it's implemented inside. ClaimClassifier.classify(extraction: ExtractionResult): Promise<ClaimClassification> is a contract. The body can change completely — swap the ML model, change the vendor — and every caller keeps working as long as the contract holds. Contracts are what let you review a module's promise without reading its implementation, and what let an AI agent regenerate the inside of a module safely.

Clean Code & Naming

Names are the cheapest documentation that exists, and the only documentation that can't drift out of sync with the code, because it is the code. calcRisk(c) tells you nothing. calculateFraudRiskScore(claim: Claim): RiskScore tells you what it computes, on what, and what it returns — you can review the call site without opening the function. If you can't tell what a function does from its name and signature alone, an AI agent didn't write clean code; it wrote something that compiles.

Version Control & Code Review

Git branching and pull requests exist to make change reviewable, revertible, and attributable. A branch isolates work in progress from what's deployed. A pull request is the checkpoint where a second party — human or, on this team, the architect reviewing an AI agent's output — confirms the change does what it claims before it merges. See the full Branching & Pull-Request Workflow for ClaimSense's concrete rules, and the Code Review Checklist for the gate every PR passes through.

The Testing Pyramid

Not all tests are worth the same. Unit tests are cheap, fast, and should be the majority of your suite (~70%) — they test pure logic in isolation. Integration tests (~20%) confirm modules cooperate correctly against a real dev database or a mocked external API. End-to-end tests (~10%) are slow and brittle but prove the whole system works from a user's perspective — use them sparingly, for the flows that matter most. A suite that's mostly E2E is inverted and a warning sign, not a strength. See the full breakdown and ClaimSense's numbers in Engineering KPIs and the Test Plan.

Technical Debt

Technical debt is a shortcut taken deliberately, with the interest payment understood — not a synonym for "bad code." Shipping RoutingEngine with a hardcoded adjuster-region map instead of a configurable rules table, because the real rules table is 3 sprints out, is debt if it's written down, scoped, and scheduled. The same shortcut shipped silently, discovered by whoever hits the bug six months later, is just a defect wearing a nicer name. Your job as reviewer is to ask an AI agent's shortcuts to justify themselves out loud.

DRY & SOLID (lightly)

DRY — Don't Repeat Yourself. If the same risk-weighting logic appears in three places, a future change to fraud rules will get applied to two of them and someone will spend a day debugging the third. Extract it once real duplication (3+) shows up — not preemptively.

SOLID, briefly: Single responsibility (one reason to change), Open/closed (extend behavior without editing stable code), Liskov substitution (a subtype must honor its parent's contract), Interface segregation (don't force callers to depend on methods they don't use), Dependency inversion (depend on abstractions, not concrete vendor SDKs). You don't need to recite these — you need to recognize when an AI agent's output violates one and ask why.

Error Handling

An empty catch block is a production defect, not a style nit — it converts a knowable failure into an invisible one. Every external call (the OCR/extraction API, the notification provider, the database) needs an explicit timeout, a bounded retry strategy, and a decision about what happens when retries are exhausted. "It worked in my test" is not a failure mode analysis. See the TDD's Risks & Trade-offs and the failure-path rows in the Test Plan.

Good vs Bad Code

Same requirement — compute a fraud/risk score for an incoming claim — two very different outputs an AI agent might hand you. Reading both side by side is faster training than any rule list.

Reject — looks done, isn't reviewable
function calc(c) {
  let s = 0;
  if (c.amt > 10000) s += 30;
  if (c.days < 2) s += 20;
  try {

}
Approve — reviewable in one pass
/** Weighted 0-100 fraud/risk score. See TDD §5. */
function calculateFraudRiskScore(
  claim: Claim,
  history: ClaimHistoryEntry[]
): RiskScore {
  const signals: RiskSignal[] = [
    highValueSignal(claim.estimatedAmountCents),
    rapidFilingSignal(claim.lossDate, claim.filedDate),
    priorClaimFrequencySignal(history),
    totalLossLanguageSignal(claim.description),
  ];

  const score = clamp(sumWeighted(signals), 0, 100);
  return { score, signals, computedAt: new Date() };
}

The Architect's Review Lens

When an AI agent hands you a pull request, you are not reading it the way another engineer would. You're reading it for these seven things, roughly in this order:

  1. Does it match the TDD? If the implementation quietly diverges from the agreed approach, that's a design conversation, not a code nit — stop and ask why before you look at anything else.
  2. Is the contract explicit? Typed inputs, typed outputs, enumerated errors. If you have to read the function body to know what it returns, the contract isn't done.
  3. What happens when it fails? Timeout, retry policy, and recovery path for every external call. No silent catch.
  4. Is it idempotent where it needs to be? Anything that sends an email, writes a row, or calls a paid API must survive being run twice with the same input.
  5. Are the tests assertions of behavior, not of implementation? A test that breaks the moment you rename a private variable is testing the wrong thing.
  6. Is the blast radius what the PR size implies? A 40-line diff touching one module is a fast read. A 40-line diff touching six modules is a hidden large change — see PR size rules.
  7. Would a junior developer understand this in six months with no other context? If the answer is no, it's not done — it's just merged.
Non-negotiable

An AI agent that produces code passing every automated check but that you cannot explain in your own words is not ready to approve. Automated green checkmarks are necessary; they are not sufficient. Your signature on the sign-off block means you understood it, not that CI did.

1. Context

Claims currently reach adjusters through three unconnected channels — a mobile app photo upload, an inbound email box, and a web portal form — and every claim is manually read, categorized, and assigned by a triage clerk before an adjuster ever sees it. Median time from submission to adjuster assignment is 14 business hours. High-value and likely-fraudulent claims receive the same first-pass handling as a routine windshield chip, which delays the claims that most need early attention and slows the ones that don't.

ClaimSense automates the triage step: ingest the claim regardless of channel, extract structured fields from attached documents and photos, classify the claim by type and severity, score it for risk/fraud indicators, and route it to the correct adjuster queue with an SLA clock — while keeping a human adjuster as the final decision-maker on anything flagged or above a value threshold. ClaimSense triages; it never approves, denies, or pays a claim.

2. Chosen Approach

Event-driven pipeline of small, independently deployable services, coordinated through an internal event queue rather than direct synchronous calls, so that a slow or failing external dependency (the OCR/LLM extraction vendor) degrades gracefully instead of blocking claim intake.

Why this shape matters for review

Notice that only three modules touch I/O directly (DocumentExtractionService, RoutingEngine, NotificationService) and only one of those calls an external vendor. ClaimClassifier and RiskScoringEngine are pure functions — no network, no database, no clock except an injected timestamp. That's deliberate: pure logic is where most of the business rules live, and pure functions are the cheapest thing in this system to unit test exhaustively. See the Test Plan's unit-tier row counts.

Formatting

  • 2-space indentation, no tabs. Enforced by Prettier; not a matter of taste or debate.
  • Semicolons required, always. No ASI-dependent code.
  • Single quotes for strings except when the string itself contains a single quote.
  • Max line length 100 characters, soft-wrapped by the formatter.
  • One statement per line. No if (x) doThing(); on one line — braces always, always on their own structure.

Comments

Default: no comments

A well-named function and a typed signature already say what the code does. Only comment the why — a non-obvious constraint, a workaround for a specific vendor bug, an invariant that isn't visible from the code itself. If deleting the comment wouldn't confuse the next reader, delete it.

Reject
// increment the counter
counter++;

// this function calculates the risk score
function calculateFraudRiskScore(claim, history) { ... }
Approve
// Vendor OCR occasionally returns confidence as a
// percentage string ("87") instead of a 0-1 float.
// Normalize before comparing to the 0.6 threshold.
const confidence = normalizeConfidence(raw.confidence);

TypeScript Contract Rules

  • tsc --noEmit must pass with zero errors before any PR is opened.
  • any is forbidden without an inline comment justifying it and a linked follow-up ticket. unknown is almost always the correct choice instead.
  • Every exported function has an explicit return type — never rely on inference for public contracts.
  • Zod schemas are the single source of truth for HTTP boundary types; the TypeScript type is derived with z.infer<typeof Schema>, never hand-duplicated.

Error Handling Style

Reject — forbidden patterns
try {
  await extractionApi.call(doc);
} catch (e) {}                     // silent swallow

try {
  await extractionApi.call(doc);
} catch (e) {
  throw e;                          // re-throw, no context
}

catch (e) {
  console.log("error: " + e);       // unstructured, no class
Approve
try {
  return await extractionApi.call(doc);
} catch (e) {
  logger.error({
    event: "extraction_call_failed",
    error_class: classifyError(e),  // "UpstreamTimeoutError" etc.
    correlation_id: correlationId,
    claim_id: claim.id,
  });
  throw new UpstreamUnavailableError(claim.id, { cause: e });
}

Module Structure

  • One responsibility per file — see the Module Composition Rule: soft target ~300 lines, hard ceiling 500.
  • No circular imports. If two modules need each other, extract the shared piece into a third.
  • Business logic modules (backend/src/services/) never import Express request/response types — that couples pure logic to the transport layer.

Applies Equally to AI-Generated Code

No exceptions clause

"The AI agent generated it this way" is not a justification for a house-style violation in review. If an AI agent's output uses any, swallows an error, or produces a 700-line file, the fix is the same as it would be for a human's PR: send it back.

New module respects its stated single responsibility (Module & API Design §)BlockingScope creep in a module is how a 300-line file becomes an 1,100-line file no one wants to touch.

2. Contracts & Types

CheckGateRationale
tsc --noEmit passes with zero errorsBlockingNon-negotiable contract enforcement per Coding Standards.
No new any without an inline justification comment and linked ticketBlockingany is a hole in the contract the compiler can no longer check.
Every exported function has an explicit, reviewed return typeBlockingCallers should never need to read a function body to know its contract.

3. Failure Paths & Resilience

CheckGateRationale
Every external call (extraction API, DB, email provider) has an explicit timeoutBlockingAn unbounded call is an outage waiting for a slow day.
No empty or silent catch blocks anywhere in the diffBlockingA swallowed error converts a knowable failure into an invisible one.
Retry strategy is bounded and documented (max attempts, backoff curve)BlockingUnbounded retry is an explicitly prohibited pattern — see Stall Detection rules.
A defined recovery path exists when retries are exhausted (dead-letter, manual review queue, escalation)Blocking"It works in dev" is not a failure-mode analysis.
Errors are tagged with a stable error_class before loggingAdvisoryGeneric Error in logs blocks fast triage; fix in this PR or the very next.

4. Idempotency

CheckGateRationale
Any new side effect (row insert, email send, routing decision) is gated by an idempotency keyBlockingA retry-unsafe operation is a production incident on its second run, not an edge case.
Running the operation twice with the same input is covered by an explicit testBlockingUntested idempotency is unverified idempotency.

5. Tests

CheckGateRationale
Happy path coveredBlockingBaseline requirement, not a milestone.
Failure path covered (dependency unavailable, malformed input, auth missing)BlockingHappy-path-only coverage does not satisfy Definition of Done.
Boundary cases covered (empty input, max-length input, off-by-one)BlockingBoundary bugs are the majority of real production defects in claims data.
Tests assert behavior/output, not internal implementation detailsAdvisoryImplementation-coupled tests break on harmless refactors and erode trust in the suite.

Why the limit is enforced, not suggested

Review quality drops sharply past ~400 lines — not because reviewers are lazy, but because working memory can't hold a bigger diff's interactions at once. An AI agent that returns an 1,100-line PR for "add SIU routing" is handing you something that can only be rubber-stamped, not reviewed. Ask it to split by module boundary along the lines already drawn in the Module & API Design.

Review Requirements

  • Minimum one approval before merge; PRs touching RiskScoringEngine, RoutingEngine, or anything in the auth/PII path require the AI Solution Architect's approval specifically, not just any approver.
  • All CI checks green: tsc --noEmit, lint, full test suite, and the Code Review Checklist's blocking items confirmed by the reviewer.
  • No self-merge. Even for a one-line hotfix — the whole point of the gate is a second set of eyes, including on AI-agent output the author didn't hand-write.
  • PR description states: what changed, why, what was tested, and any TDD deviation (see Checklist §1).

A change is done only when every row below is true. Not "mostly true." Not "true except for the one the deadline was tight on." A change that fails one row is not done — it is in progress, however far along it looks.

#RequirementVerification Evidence Required
1Implementation traces to a design element in the TDD and/or Module & API DesignPR description links the relevant TDD section or module contract
2Contracts are explicit: typed inputs, typed outputs, enumerated error classestsc --noEmit passes; reviewer confirms signature completeness against Checklist §2
3Happy path, failure path, boundary cases, and idempotency are all testedTest file diff shows all four categories present per Test Plan mapping
4No silent failure: every catch block logs a classified error or is explicitly justifiedReviewer confirms zero empty/generic catch blocks in the diff

Automated green is necessary, not sufficient

Rows 3, 5, 6, 7, and 9 above can be checked by CI. Rows 1, 4, 8, and 10 require a human — specifically, you — to have actually read and understood the change. An AI agent's PR with every CI check green and no architect who understood it is not done. It is unreviewed code that happens to compile.
